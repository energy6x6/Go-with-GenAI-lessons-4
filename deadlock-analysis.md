# Аналіз дедлоку (Частина 2)

## Код, що аналізується

```go
var wg sync.WaitGroup
ch := make(chan int)
wg.Add(1)
go func() {
    ch <- 42
    wg.Done()
}()
wg.Wait()
fmt.Println(<-ch)
```

## Мій промпт до ШІ

Проаналізуй наведений код Go. Не просто перепиши його: поясни точну
послідовність переплетення горутин, що веде до дедлоку. Для кожної
горутини назви операцію, на якій вона блокується, і подію, на яку чекає.
Чому wg.Wait() перед читанням з небуферизованого каналу зупиняє виконання?
Чи допоможе інший порядок запуску горутин? Запропонуй мінімальне
виправлення та поясни, чому воно прибирає циклічне очікування.

## Пояснення від ШІ

1. main створює небуферизований канал і встановлює лічильник WaitGroup у 1.
2. main запускає горутину-відправника. Запуск не означає, що вона вже завершила роботу.
3. Якщо main першим доходить до wg.Wait(), він блокується до виклику wg.Done().
4. Відправник доходить до ch <- 42 і блокується: небуферизоване надсилання
   потребує готового отримувача. Тому наступний wg.Done() не виконується.
5. Єдиний отримувач — main, але він читатиме канал лише після повернення
   з wg.Wait(). Утворюється цикл: main чекає Done, відправник чекає читання main.
6. Якщо відправник запуститься раніше, він спочатку заблокується на надсиланні,
   а main потім на Wait. Результат той самий: планувальник не усуває залежність.

Це дедлок, а не гонка даних. Детектор -race не замінює перевірку завершення
програми; готові тести обмежують очікування тайм-аутом.

## Мінімальне виправлення

У deadlock/fixed.go прибрано зайвий WaitGroup: горутина надсилає 42,
а Run одразу читає канал і повертає значення. Надсилання та отримання
синхронізуються самим каналом, тому циклічного очікування немає.
Для одного читання закривати канал не потрібно: тут немає range,
якому потрібен сигнал завершення потоку.
